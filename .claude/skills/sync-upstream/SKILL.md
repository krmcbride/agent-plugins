# Sync a vendored plugin with upstream

A vendored plugin has three parts:

- `vendor/<name>/upstream/` is upstream's files, byte for byte. Never edit it by hand. `sync` replaces it.
- `vendor/<name>/upstream.json` pins the upstream repo, path, commit, and version.
- `vendor/<name>/claudify.mjs` and `vendor/<name>/patches/` record every difference from upstream:
  - `drop` lists paths to leave out.
  - `rules` are find-and-replace rules for renames that repeat across files.
  - `generate` writes files upstream lacks, such as `.claude-plugin/plugin.json`.
  - Each patch rewrites a passage. Its header says why, and its `Kind` is `claudify` for Claude Code porting or `personal` for the owner's own changes.

`plugins/<name>/` is generated by `node scripts/vendor.mjs build <name>`, and its `UPSTREAM.md` lists every change. Never hand-edit `plugins/<name>/` without recording the edit with `save-patch`, because the next build overwrites it and CI fails while it differs.

After the patches apply, the build scans `skills/` and `agents/` for Cursor terms. Each hit needs an allow entry that says why it is fine in Claude Code. The build fails on the first patch that does not apply, on a rule, drop, or allow entry that matches nothing, and on any unallowed term.

## Steps

Run every command from the repository root. The examples use `pstack`.

1. Start a branch from the latest default branch: `git fetch origin master && git switch --no-track -c sync/pstack origin/master`.
2. Run `node scripts/vendor.mjs sync pstack`. If it says vendor is already at upstream, stop. There is nothing to sync and no PR to open. Otherwise keep its output. It lists the upstream commits for the PR description.
3. Commit only `vendor/pstack/upstream` and `vendor/pstack/upstream.json`, with the subject `Sync pstack upstream to cursor/plugins@<short sha> (<version>)`. Keep this commit separate so reviewers can read upstream's own changes as one diff.
4. Run `node scripts/vendor.mjs build pstack` and fix each `FAIL` line, then build again until it prints `plugins/pstack built.` Fix them in the order the build reports them:
   - **A patch does not apply.** `plugins/pstack` now holds the tree from before that patch. Read the patch's header and diff, make the same change by hand in `plugins/pstack` against the new upstream wording, then run the `save-patch` command the message prints. That keeps the header and rewrites the diff. If upstream already made the change, delete the patch file.
   - **A rule matched nothing.** Upstream reworded or removed what it targets. Search `vendor/pstack/upstream` for the new wording. Update the rule's `find` if the translation is still needed, or delete the rule if it is not.
   - **A term is not translated or allowed.** Choose one fix. Use a rule when the same rename applies wherever the term appears, and extend an existing rule before adding a new one. Use a patch when the passage needs new wording: edit `plugins/pstack`, then run `node scripts/vendor.mjs save-patch pstack <short-name>` and fill in the header it writes. Use an allow entry only when the term cannot misdirect an agent, and write the reason. Never allow a tool, parameter, path, or model name that Claude Code lacks, because an agent would try to use it.
   - **An allow entry or drop matches nothing.** Remove it.
5. Read upstream's diff from step 3 (`git diff HEAD~1 HEAD -- vendor/pstack/upstream`) for Cursor dependencies the scan cannot see. Look for new skills or playbooks, new tool or subagent fields, and changed meaning in a passage a patch rewrites. Translate what you find. If a new Cursor term could return in later syncs, add it to `scan.terms`.
6. Verify:
   - `node scripts/vendor.mjs check pstack` prints `plugins/pstack is up to date.`
   - `claude plugin validate .` and `claude plugin validate plugins/pstack` pass, if the `claude` CLI is available.
   - `git diff HEAD~1 -- plugins/pstack` reads correctly. Upstream's changes should come through translated, and nothing else should move.
7. Commit `vendor/pstack/claudify.mjs`, `vendor/pstack/patches`, and `plugins/pstack` together, with the subject `Carry pstack's Claude Code changes to upstream <short sha>`. Its body names each rule, patch, or allow entry that you added, changed, or removed, and why.
8. Push the branch and open a pull request. Its description lists:
   - the upstream commits from step 2;
   - what changed in the translation and why;
   - any call you were unsure of, so the owner can check it;
   - the verification results.

## Changing a translation or adding a personal change

Use the same tools without syncing. For a personal change, edit `plugins/<name>`, then run `node scripts/vendor.mjs save-patch <name> <short-name> --kind personal`, and write a header that says what the change is for. Patches apply in number order after the rules, so a personal patch edits the translated text. Build, check, and commit the patch with the regenerated plugin.

## Vendoring another plugin

1. Create `vendor/<name>/upstream.json` with `repo`, `ref`, `path`, and placeholder `commit`, `commitDate`, and `version`.
2. Run `node scripts/vendor.mjs sync <name>`.
3. Write `vendor/<name>/claudify.mjs` from pstack's as a model.
4. Build, and add a marketplace entry with `"source": "./plugins/<name>"`. CI checks every `vendor/*/` directory on its own.
